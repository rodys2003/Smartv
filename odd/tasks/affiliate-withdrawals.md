## Shared contract
New module `src/features/affiliates/services/affiliateFinanceService.ts` owns:
- `FinanceRate { cop_per_usdt: number | null; version: number; updated_at: string | null }`.
- `WithdrawalQuote { affiliate_id: string; commission_ids: string[]; cop_amount: number; usdt_amount: number; cop_per_usdt: number | null; rate_version: number; gross_usdt: number; fee_usdt: number; net_usdt: number; eligible: boolean; binance_uid: string; quoted_at: string }`.
- `getFinanceRate(): Promise<FinanceRate>`; `setFinanceRate(rate: number, reason?: string): Promise<FinanceRate>`.
- `getWithdrawalQuote(affiliateId?: string): Promise<WithdrawalQuote>`; `requestQuotedWithdrawal(quote: WithdrawalQuote, requestId: string): Promise<AffiliatePayout>`; `markPayoutProcessing(payoutId: string): Promise<void>`.
- `getFinanceAudit(): Promise<FinanceAudit[]>`, where `FinanceAudit { id: string; actor_id: string | null; action: string; entity_id: string | null; details: Record<string, unknown>; created_at: string }`.
Existing public affiliateService signatures remain compatible, but financial writes become checked RPC operations, no insecure fallbacks. `completePayoutAdmin`, `rejectPayoutAdmin`, payment confirmation/cancellation use trusted transitions. `getMyCommissions` excludes no records but must not write/promote client-side; quote derives maturity server-side. UI treats an unmatured available legacy row conservatively; displays reserved balance from payout associations. Additive `AffiliatePayout` fields may expose `request_id`, `rate_version`, `rejected_reason`, `processed_at`, `updated_at`.
Integration: administrator payment toggles (not service start) call confirmation; payment reversal cancels/reserves safely (fail if pending/paid payout requires manual reconciliation). UI must not hide mutation errors. Default existing admin email may be supported only through verified server auth identity; trusted app_metadata finance-admin permission is preferred, never user_metadata. Extra admins require documented server-side provisioning. Existing Binance UID is retained; no new network/address assumptions or automatic transfers.
